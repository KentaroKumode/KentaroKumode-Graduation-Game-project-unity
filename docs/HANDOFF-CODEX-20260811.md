## 1. ツールの叩き方

### 実行の形

測定はすべて Unity エディタの **`Tools/AutoRun/...`** メニューから起動する。
バッチはコルーチンで走り、完走時に `AutoRunLogs/chalaxis_<timestamp>.txt` を書き出す。

MCP 経由なら:

```
mcp__mcp-for-unity__execute_menu_item  menu_path="Tools/AutoRun/T4 スイープ: 5種のT4のみ (遺物なし・1000ラン)"
```

### 主要メニュー

| メニュー | 用途 | 構成 | 所要 |
|---|---|---|---|
| `T4 スイープ: 5種のT4のみ (遺物なし・1000ラン)` | T4 の値付け | 基準 + 5カテゴリ6pt + 5カテゴリ6pt+T4 + ノイズ床 = 12アーム | 約13分 |
| `挑戦 単軸スイープ (遺物なし・ノーマルAI・各1000ラン)` | 24 軸の単軸コスト | 基準 + 24段 + ノイズ床 | 約25分 |
| `挑戦 単軸スイープ: 変更した軸のみ` | 触った軸だけ再測定 | `challengeAxisSweepAxisNames` で指定 | 数分 |
| `診断: T4 単独 (基準 vs 各T4のみ・遺物なし・1000ラン)` | **T4 と基礎軸の相互作用を分離** | 基準 + 5 T4単独 + ノイズ床 = 7アーム | 約8分 |
| `T4 固着再現: A生存圧+破綻 のみ (進捗毎ラン)` | 1カテゴリだけ・毎ラン進捗 | 3アーム | 約3分 |
| `技量帯スイープ: 最適 vs 天井 (各500ラン・0pt)` | 技量帯（人間の伸びしろ）の実測 | Optimal vs Super | Super は約0.5s/ラン |
| `診断: 決定性検査 (0pt × 4アーム × 各300ラン)` | ラン跨ぎの状態持ち越し検査 | 同一設定を並べる | 数分 |

### 結果の読み方

出力は `AutoRunLogs/chalaxis_*.txt`。**必ず見る 3 点**:

1. **基準アーム（1行目）** が既知の値を再現しているか → バッチ間の地続き
2. **`[ノイズ床] 基準複製`（最終行）の 7F差分** → これより小さい差は読まない（実測 4.0pt の日もあった）
3. **`打切`列 / `rec欠落`** → 0 でなければその表は歪んでいる

判断は **McNemar p** で行う。7F差分の絶対値だけを見ない。平均値の比較は禁止（同一シードのペア比較が前提）。

### 進捗の追い方（重要）

**Unity の Console には何も出ない。** `AutoRunner.suppressLogsDuringBatch = true` が
`filterLogType = LogType.Error` を掛けているため。進捗は **`%LOCALAPPDATA%\Unity\Editor\Editor.log`** に落ちる。

```bash
grep -a "挑戦単軸" "$LOCALAPPDATA/Unity/Editor/Editor.log" | tail -3
```

- 抑止を貫通して出したいログは **必ず `AutoRunner.LogAlways()` を使う**。
  `logEnabled = true` に直接切り替える書き方は 2026-08-11 に全滅した（抑止の実装を変えた瞬間に黙る）。
- **Editor.log は Unity 再起動で消える**（`Editor-prev.log` にローテートされないことがある）。
  固着の証拠を取りたいときは再起動前に退避すること。
- Editor.log は放置すると数 GB まで肥大する。時々消す（Unity が作り直す）。

### 落とし穴（実際に踏んだもの）

| 症状 | 実際の原因 |
|---|---|
| 進捗が止まった＝重いだけ、と判断 | **CPU 使用率は無限ループと正常動作を区別しない。** `disableVSyncDuringBatch` で描画ループが全力回転するため、コルーチンが死んでいても CPU は 2 コア出る。**変化率（新しい行が到着し続けているか）を見ること。水準を 1 回見ても意味がない** |
| エディタが 3 秒周期で無応答 | `runsPerYield` が 25 だった。**1 に変更済み**（1ラン 0.13 秒なのでオーバーヘッド無視可） |
| 例外が出たのに何も残らない | `logEnabled = false` は `Application.logMessageReceived` ごと止めるので `_exceptionFlag` が立たない。コルーチンが黙って死に、番犬・反復上限・ストール検出も**同じコルーチン内なので一緒に死ぬ**。→ `filterLogType` 方式に修正済み |
| 集計に行が出ない | **0 を表示しないログは「0」と「故障」を区別できない。** 条件付き出力にしない |
| 別バッチの参照値との引き算 | `challengeCategorySweepT4Only` が 6pt アームを省いていた。**既定 false に変更済み** |
| T4 を載せたのに全アームが基準と一致 | `ChallengeResolver.IsT4Unlocked` が「カテゴリ 6pt 未達なら**黙って無効**」。→ 警告を出すよう修正済み。診断用に `IgnoreT4Unlock` を追加（スイープ終了時に必ず false へ戻る） |
| **ノイズ床を万能の物差しにする** | ノイズ床は基準の**完全複製**なのでラン単位でも 0 本しか食い違わない。一方、HP など状態を動かす処置はランを丸ごと別物にする（混沌的発散）。**その発散が生む差のばらつきは未測定**。「ノイズ床 0.0 だから 1.1 は本物」は物差しを取り違えている |
| **多重比較を数えない** | 5 アームを同時に検定するなら閾値は 0.05/5 = 0.01。p=0.027 は有意ではない |

## 2. 絶対規約（バランス作業に効くもの）

CLAUDE.md の全規約に加えて、本作業で確立したもの:

1. **調整案は採否を取ってから測定する。** 思考→自動テスト→再調整のループを勝手に回さない。
   具体値の一覧を出して承認を得る。
2. **指標ひとつで原因を断定しない。** 計装を先に入れる。
   「発動しているか」を数えてから値をいじる。数えずに値を上下させて 3 回外している
   （長引く負傷 / 浅い眠り / 不器用）。
3. **シード固定＋ペア比較**。McNemar 検定。平均比較は使わない。
4. **`null` は「無し」ではなく「触らない」**（`AutoRunner._pending*`）。
   合計 pt の一致は同条件を意味しない。
5. 「ダイス合計+N」は**禁止語彙**。攻撃+N / 出目+N / 端子配線合計+N を使う。
6. **ダイス個数（振る本数）と合計値（出目の和）を常に分ける。**
7. `RelicAxis` / `RelicCurse` / `RoleKind` / `ChallengeAxis` の **enum 順序を変えない**（int で保存済み）。
8. `BALANCE_CHANGELOG_*.md` / `BALANCE_TIER_LIST_*.md` は BOT 自動生成。**手で触らない**。
9. 何かを提案する前に **[GAME.md §24](GAME.md) と [design-rejects.md](design-rejects.md) の両方**を読む。

## 4. 【最重要】旅団契約システムを削除した（2026-08-11）

### 結論を先に

**契約は削除済み。** 復活させる前に本節と [GAME.md §24-1](GAME.md) を読むこと。
以下は「なぜ削除に至ったか」の経緯。

### 削除した範囲

| 対象 | 内容 |
|---|---|
| コード | `Assets/Scripts/GameLoop/Contracts/` 全 10 ファイル、`AutoTest/ContractAiPicker.cs` |
| 状態 | `RunState.activeContracts` / `contractsExpiredThisLayer` / `circusHandedOver` |
| フック | CombatManager（戦闘開始・ターン終了・戦闘終了・影武者の致死復活・HP20%解除）、GameManager（層開始/終了）、HopeSystem（希望減衰軽減） |
| 計装 | AutoRunner の `BuildContractBlock` / `BuildContractTierBlock` / CombatRec の契約欄一式 |
| データ | `event_list.txt` の〈別れのキャラバン〉、`EventEffectType.CircusHandover` は enum 順序維持のため残置し実行のみ無効化 |
| docs | GAME.md §12 を廃止告知に置換、§24-1 に経緯を記録 |

### 削除の理由（3 つが重なった）

1. **長期間死んでいたのに誰も気づかなかった。** 症状が「減る」ではなく「消える」で、
   集計に行が 1 行も出ない**沈黙**だった。存在感がその程度だった。
2. **HP を削るデバフの効果を打ち消す出口になっていた。** `CheckHpReleaseRule` は
   HP20% 未満で契約を全解除する ── **罰を与える動作がそのまま救済の引き金を引く**構造で、
   挑戦デバフの設計と正面から衝突する。
3. **復活させると基準が 10.4pt 下がる。** その難易度予算を、
   プレイヤーが選べない固定の税として払い続けることになる。

### 復活させる場合の前提

- **HP20% 解除ルールを外す**こと
- **BOT 評価テーブルを現行の経済スケールで引き直す**こと
- 維持費と効果の収支が黒字になる根拠を実測で示すこと。
  「取ると弱くなる選択肢」を復活させる意味はない

## 4-B. 経緯：契約システムが死んでいた（記録）

### 何が起きていたか

**BOT は 12,000 ラン で契約を 1 件も締結していなかった。**

```
前哨基地 5.66 回/ラン / 提示 20.34 / 採用 0.00 / 締結 0.00 / 到着時の所持金 平均 45.0G
```

前哨基地は回り、提示も潤沢、所持金もある。**AI の評価関数が全提示を見送っていた。**

原因は **2026-08-10 の経済リスケール**。`ContractCost.For(1)` を 3G → **15G**（×5）にしたが、
`ContractAiPicker.BaseValueL1`（値域 2〜8、コメントに「コスト3G に対しての主観評価」と明記）を
据え置いた。採用条件は `value >= cost × 1.5` なので必要値が 4.5 → **22.5** に跳ね、
テーブル最大値 8 でも到達不能になっていた。

### 修正

`ContractAiPicker.ValueScale = 5f` を新設し、`ValueAtLevel()` の返り値に掛けた
（価値を返す唯一の関数なので、採用判定・延長判定・維持費不足の切り捨ての 3 経路が一度に揃う）。
敵対ペナルティ（−6/−3/−1）も同じ尺度なので ×5 した。

リスケール前と**厳密に同じ採否**になる: 旧 `v ≥ 3×1.5` ⟺ 新 `5v ≥ 15×1.5`。

### 影響（重大）

**2026-08-11 の測定値はすべて「12 旅団が 1 つも締結されない世界」のものだった。**
契約を修正して測り直した結果が §5 の表（基準 21.0%）。
**そして契約を削除したので、それも既に古い。**

修正時に判明したこと:

- 契約は **BOT を 10.4pt 弱くしていた**（7層クリア 31.4% → 21.0%、支出G 232 → 139）。
  GOLD の 4 割近くが契約に流れ、装備が買えなくなる。
- **カテゴリ間の格差が平らになった**（B −16.0 → −12.3、全体で 1.6倍 → 1.37倍の開き）。
  契約という共通の重石が全カテゴリに乗ったため。削除で元に戻る可能性が高い。
- **「最後の審判」の +1.4pt の正体が判明した。** 契約解除の実測が
  審判アームだけ 0.63 件/ラン（他は 0.18〜0.29）、解除層も深い（5.26 vs 4.48）。
  **刻限が HP を 20% 未満へ押し下げ、契約を剥がしていた。**
  契約 0 件では検証不能だった仮説が、修正で検証可能になり、支持された。
  → 契約削除でこの経路は消えたので、審判は素直に効くはず。**要再測定。**

### 教訓

症状が「契約が減る」ではなく「契約が**消える**」＝集計に行が 1 行も出ないという**沈黙**だったため、
発覚が遅れた。**ゼロを表示しないログは、ゼロと故障を区別できない。**

## 5. 現行タスク（T4 の値付け）

### 目的

挑戦スコアの T4（各カテゴリの最上位デバフ、4pt 相当）を適正コストに収める。
`7F差分` = 基準の 7層クリア率からの差。T4 単体のコストは
**「カテゴリ6pt+T4」−「カテゴリ6pt」**（同一バッチ内で引く）。

> ⚠ **目標帯「−8〜−12pt」は再導出が必要。** あれは基準 7層クリア **31.4%** の頭上を前提に
> 決めた値。頭上が変われば適正コストも変わる。**先に配点と目標帯を決め直すこと。**

### 実測 ①（契約削除後・12アーム・各1000ラン・同一シード）— **これが現行の正**

基準: 平均到達層 5.66 / 5層クリア 61.1% / **7層クリア 31.4%** / ノイズ床 0.0

> 契約削除後の表は、契約が締結されなかった世界（05:43 バッチ）と**ビット単位で完全一致**した。
> 削除が余計な副作用を持たなかったことの確認になっている
> （`GameRng` の名前付き部分列が互いに独立していることの裏も取れた）。

| カテゴリ | 6pt | 6pt+T4 | **T4 単体** |
|---|---|---|---|
| A生存圧 | −12.2 | −17.3 | **破綻 −5.1** |
| B敵強化 | −16.0 | −20.3 | **鋼の皮膚 −4.3** |
| C戦闘則 | −10.0 | −17.7 | **凶運 −7.7** |
| D経済 | −12.5 | −18.7 | **破産 −6.2** |
| E崩壊 | −14.0 | −12.6 | **最後の審判 +1.4** |

### 実測 ②（T4 単独診断・基準の上に T4 だけ）

**配点としては不正な組み合わせなので値付けには使わない。** T4 と基礎軸の相互作用を分離するための診断。

| T4 単独 | 7層クリア | 7F差分 | McNemar |
|---|---|---|---|
| 凶運 | 23.4% | −8.0 | 31/111 (p=0.000) |
| 鋼の皮膚 | 24.5% | −6.9 | 36/105 (p=0.000) |
| 破産 | 27.5% | −3.9 | 113/152 (p=0.019) |
| 破綻 | 28.4% | −3.0 | 86/116 (p=0.041) |
| **最後の審判** | **32.5%** | **+1.1** | 16/5 (p=0.027) |

**読み方**: 6pt の上に載せた時（実測①）と単独（実測②）を比べると、
凶運は −7.7 / −8.0 でほぼ一致（相互作用なし）だが、
破産は −6.2 / −3.9、鋼の皮膚は −4.3 / −6.9 と差がある（基礎軸との噛み合わせがある）。

### T4 の現行仕様

| カテゴリ | T4 | 効果 |
|---|---|---|
| A生存圧 | **破綻** | 有利マス（休憩/秘宝/交換）を踏んだ瞬間、**15%** で空白化。固有イベントが起きる |
| B敵強化 | **鋼の皮膚** | 敵が各戦闘 1 回だけ致命傷を HP1 で耐える ＋ **ボス最大HP ×1.20** |
| C戦闘則 | **凶運** | ラン開始時に全16役から**ランダム 2 つ封印**（ラン中永続） |
| D経済 | **破産** | 開幕 GOLD **−10** / 売却額 **−20%** |
| E崩壊 | **最後の審判** | ラン累計戦闘ターン **125T以降**、**すべての被ダメージ×1.30** |

### 未解決の論点

**① B のベースが重い** — B の 6pt が −16.0 で全カテゴリ最重量。
T4〈鋼の皮膚〉を目安内（×1.40 で −9.8）にすると B 全体が −25.8（7層クリア 5.6%・3F止まり 17.1%）になり、
B を選んだ時点でランが成立しない。**T4 ではなく B のベース軸を軽くするのが筋。**

**② 4 つの T4 が目安（−8〜−12）に届いていない** — ただし目安自体が要再導出（上の ⚠）。

**③ 〈最後の審判〉が効かない** — 次節。

## 5-B. 【解決済み】〈最後の審判〉が効かなかった

### 結論（2026-08-11 追試）

> **現行仕様（2026-08-11 再変更）:** 刻限は125T。超過後は回復阻害を行わず、
> すべての被ダメージを **×1.30** する。以下は旧方式を決めた際の検証記録として残す。

- 別シード帯 70000〜70999 では、旧HP減少版は基準 **32.9%** → 審判 **33.1%**
  （+0.2pt、改善7/悪化5、McNemar p=0.774）。**+1.1pt は再現せず、バフ化ではなかった。**
- 旧 `回復 225,538` はHP上限適用前の要求量で、生存ランほど刻限後のターンと回復機会を積む
  生存者バイアスも含んでいた。計装を実回復へ修正した。
- 回復半減版は単独で −4.5pt だが、正式条件では E6pt **16.8%** → E6pt+審判 **15.7%**
  （追加 −1.1pt）と不足。E基礎軸が先にランを短くし、刻限後の回復機会を減らす相互作用による。
- **当時の採用版（現在は廃止）: 120T以後は回復不能。** 正式条件で E6pt **16.8%** → E6pt+審判 **10.5%**、
  T4追加コスト **−6.3pt**。他T4の現行 −4.3〜−7.7pt 帯へ収まった。
- 採用版のログ: `AutoRunLogs/chalaxis_20260811_080721.txt`。基準複製は完全一致、打切0。

死亡と余剰回復が両立した理由も分離できた。回復半減版の刻限超過ランでは、死亡359ランが平均
`被ダメ196.0 / 回復要求161.4 / 実回復88.1`、生存287ランが
`被ダメ83.9 / 回復要求246.2 / 実回復101.0`。全体合算では見えなかったが、死亡ラン単位では明確な赤字だった。

### 症状

素の基準の上・**契約なし・遺物なし・カテゴリ基礎軸なし**で、
1 ラン 258 HP を削ってなお 7層クリアが **31.4% → 32.5%（+1.1）**。

計装は「発動していない」を完全に否定している:

```
刻限の削り 35,245 回・164,959 HP (最大 22/T) → 超過ラン 639 本 = 1ラン 258 HP
超過後  被ダメ 107,555 / 回復 225,815 / 刻限 164,959
        刻限は被ダメの 153.4% / 回復の 73.1%
刻限超過ランの到達層  5F 21.6% / 6F 25.5% / 7F 52.9%
致命打 65 回
```

**刻限は敵の総攻撃量の 1.5 倍を、7層まで行くランに対して削っている。**
それでいて経済・ビルド・到達層のすべてが基準と一致する:

| | 基準 | 単独:審判 |
|---|---|---|
| 獲得G / 支出G / 残金 | 250 / 232 / 50.9 | 250 / 232 / 50.9 |
| 購入計 / 装備力 | 20.19 / 56.6 | 20.18 / 56.5 |
| 平均到達層 / 5層クリア | 5.66 / 61.1% | 5.67 / 60.8% |
| **7層クリア** | 31.4% | **32.5%** |

### 潰した仮説（2 つとも実測で否定）

**❌ 契約の HP20% 解除** — 「刻限が HP を 20% 未満へ押し下げ、契約を剥がして得をさせている」。
契約がある世界では審判アームだけ解除 0.63 件/ラン（他アーム 0.18〜0.29）・解除層も深い（5.26 vs 4.48）
という差が出ていたので支持されたと判断したが、**契約を完全に削除しても +1.1 は残った**。
差は HP を削った結果であって、+ の原因ではなかった（相関を因果と読み違えた）。

**❌ 救済（灯火 / ラストスタンド / フルーレ）の現金化** —
`LastStand.TryConsumeRevival` は HP0 で**全回復**する（灯火＝一度きり全回復、ラストスタンド＝満タン復活）。
「40 削って 93 まで戻る＝削られた方が得」「灯火はボス戦で発動しないので持ち越すと死に札、
刻限が道中で焼却してくれる」という仮説を立てたが、実測は否定:

```
                灯火 / ラストスタンド / フルーレ / 戻したHP計
基準             39 /  0 /  75 / 3492
単独:最後の審判  38 /  0 /  75 / 3400   ← 基準とほぼ同じ、むしろ少ない
[ノイズ床]       39 /  0 /  75 / 3492   ← 基準と完全一致
```

### いま最も疑うべきこと: **+1.1 は実在しないかもしれない**

- McNemar は 16改善/5悪化・**p=0.027**。だが**5 アームを同時に検定**しているので
  Bonferroni 閾値は 0.05/5 = 0.01。**有意ではない。**
- **ノイズ床は対照になっていない。** ノイズ床は基準の完全複製なのでラン単位でも 0 本しか
  食い違わない。一方、HP を動かす処置は戦闘の長さを変え、以降の乱数消費をずらして
  **ランを丸ごと別物にする**。この混沌的発散が生む 7F差分のばらつきは**一度も測っていない**。
  実際、救済の発動回数はアーム間で 61〜101 と大きく振れている。

**次の一手（実施済み）**: 同じ審判アームを**別のシード帯**で引き直した。
実在するなら再現し、発散ノイズなら消える。**これが決まるまで対処を議論しても意味がない。**

### 実在しなかった場合の対処方針

症状は「デバフがバフになっている」ではなく **「効果が完全に無害化されている」**。
超過後の回復が 1 ラン 353 HP 出ており、刻限の 258 HP を丸ごと吸っている。
対処は削り量ではなく **回復に吸われない削り方**:

- **最大HP を削る**（回復では埋まらない）
- **回復量そのものに刻限を掛ける**

**削り量を上げるのは禁止。** 55,772 → 112,462 → 164,959 HP と 3 度増やして
7層クリアが 18.8% → 18.8% → 32.5% と、量に対して単調ですらない。

## 5-C. 棄却済み（再提案禁止）

- **破綻: HP 閾値割れで最大HP 半減** — 1回限り版 590 発動で −2.2pt、複数回版 981 発動で −2.7pt。

  **〈最後の審判〉と同じ「HP を削っても効かない」症状**なので、§5-B の結論次第では
  同一の原因（回復余剰による吸収）である可能性がある。
- **最後の審判: 3層・5層で大罪を 1 つ付与** — UI 未実装で抽選付与になり、効果が恒久デバフ任せで読めなかった（−6.4pt）。
- **浅い眠り: 回復スポットに最大HP比の上限** — 3 度測って一度も効かず。回復量が最大HP の 30% なので
  HP 40% で寄るとちょうど上限に着地し、一度も噛まなかった（発動率 2.4%）。→〈遅い回復〉（全回復 ×0.70）へ差し替え。
- **不器用: 端子の種類数上限 / 1ターンの配線本数上限** — 強いビルドほど素通りする。→〈綻び〉（端子封印）へ差し替え。

## 6. 〈破綻〉の固有イベント（2026-08-11 実装）

有利マスが空白化したとき、**効果も選択肢もない**フレーバーイベントが起きる。

- 定義: `Assets/Resources/Events/event_list.txt`、条件は **`召喚専用`**（通常抽選には出ない）
- 4 種を用意し、空白の理由を毎回変えてある:
  **国破れて山河あり**（自然に還った）/ **兵どもが夢の跡**（時間が経ちすぎた廃墟）/
  **先客**（人間に先を越された）/ **間違いのない地図**（地図の方が古い）
- 抽選は `GameManager.VoidTileEventNames` から。
  **文面の抽選は発動判定と別の乱数列**（`challenge.hatan.flavor`）から引く
  ── 同じ列を消費すると、文面を 1 種増やしただけで発動の並びまでずれてペア比較が壊れる
- 空白化は `node.activated` を立てた**後**に判定する（マップ往復で引き直せないように）
- イベントが出せなくても空白化は成立させる（不具合が「デバフが効かない」形で現れるのを防ぐ）

追加した仕組み: `EventCondition.summonOnly` / `EventParser` の `召喚専用` トークン /
`EventDatabase.IsAvailable` での除外 / `EventDatabase.GetByName` / `EventEncounter.BeginWith`。

### 計装を書くときの鉄則

1. **0 でも必ず出す。** 条件付き出力にすると「0」と「故障」が同じ『行が無い』になる。
   契約の締結 0 件を 1 バッチ見逃した原因がこれ。
2. **要求が落とされたら言う。** `IsT4Unlocked` の「条件未達は黙って無効」で
   診断アームが全部空振りし、1 バッチ無駄にした（現在は警告を出す）。
3. **抑止を貫通するログは `AutoRunner.LogAlways()` を使う。**
