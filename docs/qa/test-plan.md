ゲームの仕様の全挙動を、観点ごとに潰すための計画です。今回は**準備の段**（何を・どう・どれだけ）までで、項目書そのものはまだ作っていません。

## 1. 段取り

凍結（中身がもう動かない）した部分から消化し、全体の通しは中身の凍結の後に回します。
「凍結」の判断は機能の一覧の「凍結」の欄（`固` / `動` / `仮`）と、直近 2 週間の変更回数で決めます。

| 段 | やること | 入口の条件 | 出口の条件 |
|---|---|---|---|
| 0. 準備（今回） | 機能の一覧・観点・見積もり・書式・仕様の穴の初版 | ― | 4 つの文書が揃い、作者が仕様の穴の上位 10 件に判断（直す／仕様に書く／受け入れる）を付けた |
| 1. 仕様の穴の解消 | spec-gaps.md の 65 件に判断を付け、「仕様に書く」は GAME.md を直す | 段 0 の出口 | `重` 10 件すべてと `中` の 8 割に判断がある。期待値が書けない単位が、項目書を作る対象の中に残っていない |
| 2. 道具の整備 | 足りない道具（下の 5 章）のうち、段 3 で使う物を作る | 段 1 の出口（並行してよい） | シナリオ台・中断セーブの往復の検算・全文字列の検算が `ALL OK` で回る。不具合を 1 つ入れて検出できることを確かめた（5-3） |
| 3. 部分ごとの消化 | 凍結した部分（`固`）から項目書を作り、消化する。順番の案: K 乱数 → F-F-11 出目パーツと F-D-11 役 → F-D-15 防御と貫通 → E キーワード（毒・充電・シールド）→ J 記録と保存 → A 起動と設定 → L 表示 | その部分が `固` で、直近 1 週間に正本の変更が無い | その部分の項目の消化率 100%・合格率 98% 以上・未解決の S/A が 0 |
| 4. 動いている部分の消化 | `動` / `仮` の部分（端子の山札・ボスのダウン・航行・イベント・挑戦カード・遺物）を、作者が「凍結」と宣言した順に | 作者の凍結の宣言（issue に書く）。その後に正本が変わったら、変わった単位の項目を作り直す | 同上 |
| 5. 全体の消化 | 通しプレイ（人）と、組み合わせの BOT 通し | 全部の大分類が段 3 か 4 の出口を通った | 終了の条件（7 章）を満たす |

**作業の決まり**（memory の運用ルールから）: 調整案は採否を取ってから測定する／判断が懸かっていない測定はしない／Unity は 1 つなので確認役は 1 人に直列で渡す。

## 2. 項目数の見積もり

### 2-1. 数え方

- 単位 × 観点で数えます。**単体の項目** = 1 つの単位を 1 つの観点で確かめる項目。
- 式の中の数は機能の一覧で数えた個数（[feature-inventory.md](feature-inventory.md) の脚注）。観点の数（「正常 1 + 境界 2 + 説明文との一致 1」など）は見立てです。
- **組み合わせの項目** = 2 つ以上の単位を同時に効かせる項目。絞った後の数（2-3）。
- **画面の項目** = 人が画面で見る項目（表示・操作）。単体の項目とは別に数えます（同じ単位を「ロジック」と「画面」で 2 回数えることがある）。
- **通しプレイ** = タイトルから結末かゲームオーバーまで。人の本数と、BOT の組の数を分けます。
- すべて概算。±3 割の幅で読んでください。

### 2-3. 組み合わせの絞り方

**品 × 品（F・E）**: items.json の実際の欄で同値の組に分けます。

| 分ける欄 | 値 | 数 |
|---|---|---:|
| `axis` | 会心・出血・毒・臨界・充電・シールド・金・（無し） | 8 |
| 役割（§8-7 の列・コードの `AxisCatalog`／`EntryEffect.Table` から） | 燃料・① 数を参照・② 規則・誓約・入口・その他 | 6 |
| `rarity` | BRONZE〜LEGENDARY | 4（組の中の代表を選ぶのに使う） |

軸 8 × 役割 6 のうち実在する組は見立てで 40 前後。全部の 2 つ組は 40×39/2 = 780 本。そこから
① 同じ軸の中（6 軸 × 役割の 2 つ組 15 = 90）、② 誓約・【規則】の品 × 封じる/読む軸の品（約 57）、③ 秘宝を足さない基準 3 本
に絞って **約 150 本**。軸をまたぐ組は「誓約が封じる軸」と「規則の品が読む資源」だけを当てます（他の軸どうしは足し算にしかならない設計・§8-6「すべての〜に効く品は置かない」）。

**品 × 敵の能力（D）**: 品の「出口」8 種（主攻撃・固定ダメの枠・毒・出血・爆発・シールド・回復・充電）× 敵の能力の型 10（反射・回避・被ダメ半減〈虚体〉・偶数ターン被ダメ 1〈霊体〉・防御・割れる装甲・積み上がる装甲・構え・回復・端子を止める）= **80 本**。

**ランの構成（I・通し）**: 7 つの因子の 2 つ組の網羅（ペアワイズ）。

| 因子 | 水準（同値の組） | 数 |
|---|---|---:|
| 職業 | 剣士・騎士・狂戦士・暗殺者 | 4 |
| 挑戦の難易度 | 0 ／ 1〜3 ／ 4〜7 ／ 8〜10 | 4 |
| 遺物 | なし ／ 2 個揃え＋1 ／ 3 個揃え | 3 |
| 整備パネル | 0 点 ／ 均等（8 本 × 3）／ 振り切り（1 本 10 ＋ 7 本 × 2） | 3 |
| 主に集める軸 | 会心・出血・毒・臨界・充電・シールド・散らす | 7 |
| 深さ 3 のボス | ゴブリン王・毒沼の主・鏡の双子 | 3 |
| 深さ 5 のボス | 業火の審判官・シュヴァリエ | 2 |

全組は 4×4×3×3×7×3×2 = 6,048。2 つ組の網羅の下限は大きい 2 因子の積 7 × 4 = 28 で、生成の道具で作ると **約 30〜35 本**の見当。
ボスは乱数で決まるので、BOT はシードを選んで当てる（シードの一覧を作るのは道具の整備の段）。

## 3. 項目書の書式

1 項目 = 1 行。表計算か CSV で持ち、`docs/qa/cases/<大分類>.csv` に置く案（作るのは段 3 から）。

| 欄 | 中身 | 例 |
|---|---|---|
| 番号 | `T-<大分類>-<単位の連番>-<観点>-<連番>` | `T-D-20-V23-003` |
| 機能 | 機能の一覧の番号 | `F-D-20`（ボスのダウン） |
| 観点 | 観点の番号 | `V-23` |
| 前提 | 状態の作り方（シード・版・RunState の値・どの画面か） | 深さ 3・ゴブリン王・HP 71%・溜めのターン |
| 手順 | 1 行ずつ | ① 攻撃の端子で 2% 以上削る ② ターンを終える |
| 期待値 | 起きるべき事（仕様から書く） | 次のターンはダウン・予告 0・大技は取り消し・明けたターンは溜め |
| 期待値の出どころ | 仕様の節（`GAME.md §6-15`・`DCR §x`・handbook の節） | GAME.md §6-15 |
| 担当 | `自動` / `人` | 自動 |
| 結果 | `合` / `否` / `保留` / `対象外` | |
| 版 | 消化した版（git の短いハッシュ） | `6ea741d` |
| 不具合の番号 | GitHub の issue 番号 | `#140` |

**期待値はコードを見ずに仕様から書く**のが原則です（コードから書くと、コードの誤りを期待値に写してしまう）。
仕様に無くて書けない物は書かずに、[spec-gaps.md](spec-gaps.md) へ足して作者の判断を待ちます。
例外: 「コードにしか無い」（確かさ `コ`）の単位は、作者が「コードを正とする」と決めた物だけ、コードの注記を出どころに書いてよい（出どころの欄に `コード: file:line` と書く）。

### 4-3. 道具そのものの確認

道具が壊れを見つけるかを、作る時に 1 回ずつ確かめます: 正本の写しの値を 1 つ変える（例: `TerminalCards.HandSize` を 5 → 4、`BossDown.TakenMul` を 1.5 → 1.0、`FreeMapParams.ChaseRest` を 4 → 3）→ 検算台が落ちることを確かめる → 戻す。落ちなかったら、その規則を見ている判定が無いので足します。

## 5. 不具合の管理

### 5-1. 重さの定義

| 重さ | 定義 | 例 |
|---|---|---|
| S | 進行不能・記録の破損・決定性の破れ（同じシードで違う結果） | 一択の窓が出ず先へ進めない／中断セーブを読んで落ちる／メタ進行が消える |
| A | 仕様と違う挙動 | 予告と実際の被ダメージが違う／説明文の効果が出ない／選べないはずの選択肢が選べる |
| B | 見た目だけの誤り | 字が欠ける・はみ出す／色・印が違う／手引きが出ない（遊びは続けられる） |
| C | 要望 | 分かりにくい・こうしてほしい |

### 5-2. 1 件の欄

| 欄 | 中身 |
|---|---|
| 題 | 何がどう違うか（1 行） |
| 重さ | S / A / B / C |
| 機能・観点 | `F-x-xx` / `V-xx`（項目書の番号があればそれも） |
| 再現の手順 | **シードと版**（`GameRng` のシード文字列・git の短いハッシュ）・前提・手順・回数（何回中何回起きたか） |
| 期待値と実際 | 期待値の出どころ（GAME.md の節）を書く |
| 見つけた版 | git の短いハッシュ |
| 直した版 | 直したコミット |
| 直した人 / 確かめた人 | **直した人と別の人**（または別のセッション）が確かめる。確かめた版も書く |
| 添付 | スクリーンショット・`runs.jsonl` の該当行・中断セーブの JSON |

### 5-3. GitHub の issue とラベルの案

- ラベル: `bug`・`sev:S`/`sev:A`/`sev:B`/`sev:C`・`area:A`〜`area:M`（機能の一覧の大分類）・`spec-gap`（仕様の穴から来た物）・`found-by:qa`・`needs-verify`（直したが確かめていない）。
- 流れ: 見つける → issue（`needs-triage` を外すのは作者）→ 直す（PR に `Fixes #n`）→ `needs-verify` を付ける → 別の人が確かめて閉じる。
- 仕様の穴は 1 件 1 issue にせず、spec-gaps.md の番号で束ね、判断が付いた物から issue にする（`spec-gap` ラベル）。
- memory の決まり「issue が解決したらマージしてよい」に合わせ、`needs-verify` が外れるまでは閉じない。
