## 1. なぜ作るのか

`SuperCombatAI`（天井AI）は同一シードのペア比較で `Optimal` に勝つ。

| 条件 | Optimal | Super | 差 | p |
|---|---|---|---|---|
| 0pt・遺物なし・パーツ有り | 34.7% | 39.3% | +4.6pt | 0.007 |
| 0pt・遺物なし・パーツ無し | 18.2% | 21.1% | +2.9pt | 0.044 |

有意ではあるが**相対で 13〜16% しかない**。これが「盤面に技量の余地が薄い」のか
「Super がまだ弱い」のか区別できない。**天井の位置が未知**なので、
ADR-0010 が求めた「技量で伸びる余地」を評価できない。

近似を減らした実装を並べ、その差で Super の位置を測るのが目的。
**勝つことが目的ではない。**

## 4. 直面している問題

### 4-1. 計算量を 3 度見誤り、2 度フリーズさせた

| 回 | 誤り | 実際の規模 |
|---|---|---|
| 1 | 偶然ノードの分岐を**決定ごとに作り直し**、しかも全列挙してから刈っていた | 6×10^10 回の配列確保 |
| 2 | DP 化で①が解決したと誤認。**決定空間は縮んでいなかった** | 1.2×10^10 |
| 3 | 「葉は単純な算術」と仮定して見積もった。実際は葉が再帰の入口 | 予算 4,000 でも 1.9×10^8/決定 |

**残っている掛け算**:

```
V() 1 ノード = 手札24 × 敵8 = 192 分岐
             各分岐で Q() = 主配線 243 を全列挙
             → 46,656 演算/ノード
```

### 4-2. 戦闘ルールが 3 実装に分裂している（最重要）

```
① CombatManager           ← 正本
② SuperCombatAI.ApplyTurn ← 簡略再実装
③ ExactCombatAI.ApplyTurn ← さらにもう 1 つ
```

②③に入っていないもの:

- **敵の被ダメ軽減**（③は 2026-08-17c に追加、②は未対応）
- **敵パッシブ 全件**（6層 `AshRegrowth`/`EmberOmen`/`EmberFury`/`ScorchedPact`/`BlazeBrand`、
  7層ヴェスカの停滞スタック・天与の才の踏みとどまり・回帰性真理）
- プレイヤーのパッシブ・役の効果・会心・出血・臨界

C1（唯一の正本は実コード）に対して、**既に 2 つの偽の正本がある**。

### 4-2b. 特殊端子を「間違って」実装している（欠落ではなくバグ）

```csharp
// ExactCombatAI.ApplyTurn
switch (plan.main[i])
{
    case DiceTerminal.Attack: aSum += v; break;
    case DiceTerminal.Block:  bSum += v; break;
    default:                  cSum += v; break;   // ← 充電と特殊端子を同一視
}
```

`_termKinds` は特殊端子の装備時に 4 になる（`SpecialTerminals.EquippedLimit(run) > 0`）。
そのとき**端子 3（特殊）が `default` に落ちて充電として扱われる。**

特殊端子は 11 種あり効果もスケールも異なるので、スカラの飽和関数では表せない。
現状は「4^5 = 1024 通りを列挙し、そのうち特殊端子を含む枝を全部誤って評価している」状態。
**列挙を増やした分がまるごと無意味**になっている。

他の欠落（§4-2）は「入っていない」だが、これは「間違って入っている」ので質が違う。
**当面は `_termKinds` を 3 に固定して特殊端子の枝を作らない**方が、誤った評価より正直。

### 4-3. 状態が粗すぎて DP が異なる盤面を同一視する

```csharp
private struct S { public int pHp, eHp, turn, charge; }
```

`StateKey` に含まれない値は「同じ状態」として畳まれる。含まれていないもの:
停滞スタック / decay 系 / 役の使用履歴 / パッシブの内部値 / 烈炎スタック / 焦土契約スタック。

**深さや予算では解決しない。状態設計の欠落。**
一方で次元を増やすと DP の合流が減り、DP 化の利得が消える trade-off がある。

### 4-4. 役の発動が探索の外にある

`RolePolicy` は Optimal と共有。**ADR-0010 の中核である役システムを最適化していない。**
R2（すべてにおいて理論値）に対する明確な未達。

### 4-5. その他の近似と未実測の仮値

| 項目 | 値 | 性質 |
|---|---|---|
| `HandBranches` | 24 | 手札分布の上位のみ |
| `TopClasses` | 6 | 面クラスの上位のみ |
| `EnemyBranches` | 8 | 敵ダイス分布の上位のみ |

## 5. 打ち手の候補

### 5-1. 決定空間の縮約 ── 相異なる「合計組」を列挙する

> **2026-08-17 訂正。** 初版はここに
> 「攻撃部分集合を決めれば残りの分割は閉じた式で決まる」「243 → 約 32 に縮む」と書いていた。
> **どちらも誤り。** 閉じた式で決まるのは**飽和の上限だけ**で、上限内の配分は本物の選択である。
> 削減幅の「約 32」にも根拠が無かった（列挙して数えていない）。

**閉じた式で決まるもの（飽和の天井）**

- 攻撃: 敵を倒すのに必要な量を超える分は無駄
- 防御: 敵攻撃値を超える分は無駄
- 充電: 上限 − 現充電 を超える分は無駄

**閉じていないもの（価値関数に依存する本物のトレードオフ）**

- **防御 vs 充電** ── 防御は今ターンの被ダメを消し、充電は後のリロールを買う。
  どちらが得かは将来の価値関数そのものに依存する。上限内での比較は closed form にならない
- **攻撃 vs 防御** ── 倒せないターンに削りを進めるか生存を優先するかも同じ
- **特殊端子** ── スカラの飽和関数で表せない（§4-2b）

**正しく削減できるのは列挙の重複だけ。**
役を実装していない現行モデルでは `ApplyTurn` は端子ごとの**合計**しか見ないので、

```
3^5 = 243 個の「割り当て」 → 相異なる (aSum, bSum, cSum) の「合計組」
→ 各成分を飽和上限でクリップしてから重複を取る
→ Pareto 劣位（クリップ後の全成分が他以下）を落とす
```

**現行モデル内では厳密**だが**閉じた式ではない**。
**削減幅は未計測** ── 列挙して数える必要がある。

役を実装したときは「合計が同じでも役が違う」ので割り当てに戻る。
その場合も *相異なる (sums, 役パターン)* の列挙で足りる。

### 5-2. 敵パッシブの「宣言」を効果の隣に置く（R8 への回答）

係数は現状メソッド本体に直書き（例: `AshRegrowth` の `0.02f`）。外から引けない。

```csharp
public interface ICombatSearchHint { void Contribute(ref SearchHints h, in SearchProbe p); }
public struct SearchProbe { public int turn; public float enemyHpRatio; }
public struct SearchHints {
    public float enemyRegenRatio;      // 敵の毎ターン回復（最大HP比）
    public int   enemyDiceBonus;       // 敵ダイス合計への加算
    public float enemyDamageReduction; // 敵の被ダメ軽減
    public int   blockPenaltyPerTurn;  // 防御端子への反作用（烈炎など）
}
```

係数を `public const` へ引き上げ、`Execute` と `Contribute` が**同じ定数・同じ条件式**を共有する。
実装は 2 つだが**値と発動条件の持ち主は 1 つ**。

**副産物が重要**: 装備パッシブのうち `ICombatSearchHint` 未実装の数を数えてログに出せる。

```
[ExactCombatAI] boss_layer6: パッシブ 5 個中 3 個が探索モデル未実装
                (ScorchedPact / BlazeBrand / EmberFury)
```

モデルの穴が**観測可能な数字**になる。
（今日の教訓：廃止済み定数がログに出続けていた／実効状態が印字されていなかった、と同型の対策）

### 5-3. GPU（R6 への回答）

| 処理 | 適性 |
|---|---|
| expectimax の再帰・メモ化（ハッシュ表・分岐依存） | **最悪** |
| ターン軸の DP を層ごとに並列化（level-synchronous value iteration） | **良好** |

**DP 化が GPU 化の前提。** 順序は逆にできない。
また `Dispatch`→`GetData` の同期がミリ秒級なので、**1 決定ごとに GPU を叩く形は成立しない**
（1 ラン に数千回の決定がある）。層ごとに 1 ディスパッチなら同期は数十回に収まる。

最大の障害は性能ではなく **HLSL がルール実装 4 つ目になること**（§4-2）。

### 5-4. **本命候補: 正本を探索可能にする**

§4-2 が全ての根にある。**別モデルを作る限り、定義上「理論値」には到達しない。**
正しい方向は AI 側ではなく `CombatManager` 側の refactor:

> 戦闘解決を**副作用のない純関数** `(State, Action) → (State, Outcome)` として切り出し、
> 実ゲームと探索の**両方がそれを呼ぶ**。

得られるもの:

- 乖離ゼロ（実装が 1 つ）
- 敵パッシブ・役・プレイヤーパッシブが**自動的に**入る（R7・R8 が同時に解決）
- 状態が明示的になるので §4-3 の「粗すぎる状態」も解消
- R2「すべてにおいて理論値」が**初めて到達可能になる**

コスト: `CombatManager` は巨大で、シングルトン・ログ・イベント・`GameRng` に依存している。
純化には（a）状態の明示的な構造体化、（b）乱数の注入化、（c）副作用の分離が必要。
**ただし（b）は C2 を守るために必須の作業でもある**（探索が乱数を消費しないことの保証）。

## 7. 既知のバグ（動かす前に潰すもの）

**一度も実行できていないので、以下はコード読解による指摘。実測ではない。**

### 7-1. リロールの期待値が誤った分布で計算されている

```csharp
// ChooseReroll 内
foreach (var (hand, w) in _handBranches) {
    Array.Copy(dice, buf, _k);
    for (int j = 0; j < pick.Count; j++) buf[pick[j]] = hand[j % _k];   // ← 誤り
```

`_handBranches` は **k 個ぶんの手札**の多重集合。`m` 個だけ振り直すときの分布は
その先頭 m 要素ではない。**m 個の周辺分布を別に作る必要がある。**
現状は「上位 24 個の 5 ダイス手札の一部を流用」しており、確率が対応していない。

### 7-2. 多段ボスで「1 段撃破」を「勝ち」と誤認する

`ApplyTurn` は `s.eHp <= 0` で即 `+1`（勝ち）を返す。
しかしヴェスカは 4 段連戦で、p1 を倒しても p2〜p4 が続く（`AwakenedChainHelper.CheckAndSwap`）。
**AI は p1 を倒すために全資源を吐く判断をしうる。** 7層の評価が構造的に壊れる。

### 7-3. 形態切替でメモ化が汚染される

`_vMemo` のキーは `(pHp, eHp, turn, charge)` のみ。
`_eMaxHp` / `_eBaseAtk` / `_escProfile` は**スナップショット側**にあるので、
戦闘中に敵が別形態へ入れ替わると**前の形態の価値が残る**。
`BeginCombat` は戦闘開始時に 1 回しか呼んでいない。
→ 形態切替でクリアするか、キーに敵 id を含める必要がある。

### 7-4. 特殊端子の**装備上限**を検証していない

`SuperCombatAI` は `spec <= _specialLimit && distinct <= _termCap` で合法性を確認している。
`ExactCombatAI` は**一切検証していない**ので、上限を超える配線を返しうる。
`CombatManager` 側で弾かれる／丸められると、AI が選んだ手と実際の手が食い違う。
（§4-2b の誤処理と合わせて、特殊端子まわりは現状まるごと信用できない）

### 7-5. 静的評価と終端値の単位が違う（期待値が混ざっている）

```
終端        : 勝ち = 1.0 / 負け = 0.0   ← 確率として解釈できる
StaticValue : 0.10 + 0.80 × 進捗 × HP  ← 単なるヒューリスティック得点
```

`V()` はこの 2 つを同じ期待値の中で平均している。**単位が揃っていない。**
静的評価に落ちる枝の比率が変わると評価がバイアスする。
`StaticValue` を「推定勝率」として設計するか、混ぜない構造にする必要がある。

### 7-6. 割り当てのアロケーションが毎回走る

- `Snapshot()` は **`ChooseWiringPlan` と `ChooseReroll` の毎回**呼ばれ、その中で
  `BuildHandBranches()` が最大 4096 個の `int[5]` を確保する
- `Q()` は `new DiceTerminal[_k]` を**呼ばれるたび**確保する（V ノード × 192 回）

面構成が変わらない限り手札分岐は不変なので、**面の署名でキャッシュすべき**。
`Q()` のバッファも深さごとに事前確保すべき。GC 圧が速度を支配する可能性が高い。

## 8. モデルの妥当性に関する懸念

### 8-1. 目的関数が「戦闘勝率」で「ラン突破率」ではない

終端は勝敗の 0/1 で、**終了時の HP・充電・消耗品を評価していない**。
雑魚戦で充電を使い切って勝つのはランとしては損だが、本AIはそれを損と見ない。
`Terminal` にラン単位の価値を接続しないと、局所最適に寄る。

### 8-2. 役を適用しないまま役が発動する（不整合）

`RolePolicy` は Optimal と共有だが、`ApplyTurn` は役の効果を**一切適用しない**。
つまり探索は「役が無い世界」で配線を決め、実際には役が発動して結果が変わる。
**最適化していない**のではなく**探索の前提と実際が食い違っている**。
`SuperCombatAI` は 3 方策すべてを差し替えてこの食い違いを避けている
（コメントに「配線だけ先読みにして役の発動を貪欲のままにすると探索の前提と実際の発動が食い違う」と明記）。

### 8-3. 攻撃力・ペナルティを先のターンでも固定している

`atkBase = _pAtkPower − tele.playerAttackPenalty` を一度計算し、
**再帰の全ターンで同じ値を使う**。バフ・デバフの時間変化を無視している。

### 8-4. 充電の増え方が実装と一致していない可能性

`s.charge = min(cap, charge + cSum)` としているが、実際は毎ターンの固定加算
（`Super` の `_chargePerTurn`）や蓄電池・予備電源などのパッシブが絡む。
リロールコスト `個数 × 何回目` は仕様どおりだが、実装との一致は未確認。

### 8-5. 60 ターン打ち切りを「負け」としている

`if (s.turn > 60) return -1;` は膠着を負け扱いにする恣意的な選択。
実際の `AutoRunner` は `guard++ < 250` で回しており、値も意味も揃っていない。

### 8-6. `PowerGap()` が Super 専用なので比較が交絡する

`PowerGap()` は `wiringSkill != Super` のとき 1.0 を返す。
つまり**要求戦力によるショップのゴールド閾値調整は Super だけ有効**。
Exact は Optimal と同じ 1.0 になるので、**Exact vs Super の差には
「戦闘の読み」と「金の使い方」が混ざる**。純粋な技量差にならない。
（Optimal vs Super でも同じ交絡がある）

### 8-7. 6層だけ Super が Optimal に負けるという既知の実測

`superLayer6OptimalCombatRoutine` のコメントに、50pt・同一 10000 シードで
6層遭遇 2322 件に限ると **Optimal だけ勝利 425 / Super だけ勝利 267** と記録がある。
Exact はこの分岐を通らないので、**6層では Exact も同じ弱点を踏む可能性が高い**
（6層の敵パッシブ＝灰の再生・周期予兆・烈炎を一切モデル化していないため、原因は同じ）。

## 9. 検証計画

### 9-1. 動かす前に確認すること

1. **決定性**: 同一シードで 2 回回して**ビット一致**すること。
   本AIは乱数を使わないので、一致しなければ実装のどこかに非決定性がある
2. **予算の効き**: 決定あたりの `V()` ノード数と**予算切れの比率**を計装する。
   比率が 100% 近いなら探索は実質「静的評価」で、DP 化の意味が無い
3. **合法性**: 返した `WiringPlan` が `CombatManager` 側で丸められていないか
   （§7-4。丸められていれば AI の選択と実際の手が違う）

### 9-2. 強さの測り方

`技量帯スイープ` を使い、**同一シード・ペア比較・McNemar**。単独の平均比較は使わない。

| 比較 | 意味 |
|---|---|
| Optimal → Exact | 現行参照点からの伸び |
| Super → Exact | **天井の位置**（本題） |
| Naive → Optimal → Super → Exact | 技量帯の全段 |

**「Exact が Super に負けた」はバグの証拠にならない。**
モデルが現実と違うので、厳密に解いても弱くなりうる（§8）。
バグかモデルかを分けるには「自分の `ApplyTurn` モデル内で Optimal より高い価値を取れているか」
という**モデル内部の検査**が別に必要。

### 9-3. 統計的検出力の問題

Exact は Optimal（0.11 秒/ラン）・Super（0.42 秒/ラン）より桁で遅い見込み。
ラン数が数百に留まると、**+3pt 級の差は検出できない**。

実測済みの差の大きさから逆算すると:

| 差 | 有意になった n | 備考 |
|---|---|---|
| +4.6pt | 1000 | p=0.007（パーツ有り） |
| +2.9pt | 1000 | p=0.044（パーツ無し・ぎりぎり） |

**n=300 では +3pt は取れない。** Exact の速度が Super の 10 倍遅いなら、
1000 ラン に 70 分以上かかる。**測定計画は速度計測の結果を見てから立てる。**

### 11-3. 決定 D2 ── §5-2 の `ICombatSearchHint` は作らない

R8（係数の自動引用）への答えは**インターフェースではなく較正**にする。

`_dmgMul` / `_takenMul` は「予測した攻撃値 1 に対し実際に HP がいくら減ったか」を
指数移動平均（α=0.25）で追う。出血・毒・反射・脆弱・軽減・貫通のような
**乗算的な**チャネルは、係数を再宣言せずに実測から入る。定数が古くなる経路が無い。

**ただし較正が吸えないものが 1 種類ある: 加算的・条件付きの毎ターン効果。**

| 効果 | 実体（正本から引用） | なぜ較正で吸えないか |
|---|---|---|
| 灰の再生 | 敵 HP > 50% かつ非予兆Tのとき **毎T `max(1, floor(敵最大HP × 0.02))` 回復** | ダメージに比例しない定数。`_dmgMul` を一律に下げるだけで「毎T 64 を超えないと前進しない」という**閾値構造**が消える |
| 憤怒の残滓 | 敵 HP ≤ 50% で **敵ダイス合計 +3** | HP 段階で切り替わる条件付き加算 |

§8-7 の実測（6層だけ Super が Optimal に負ける・同一 10000 シードで
Optimal のみ勝利 425 / Super のみ 267）は、まさにこの形の誤差と整合する。

→ **決定 D3**: 加算項だけを 2 つ、モデルへ明示的に足す。定数は
`AshRegrowth` / `EmberFury` 側を `public const` へ引き上げて**そこから引用**する
（`EmberFury.Bonus` は既に `public const int Bonus = 3`）。
**これは Super にも効く**ので、6層の弱点が両 AI で同時に埋まる。

### 11-4. 決定 D4 ── モデル誤差は「推定」ではなく「印字」する

較正倍率は AI が自分のモデル誤差をどう見ているかの直接の指標なので、
**ラン集計に出す**。`DescribeCalibration()` が既にある。

[モデル残差] 敵別 与ダメ倍率 / 被ダメ倍率 (1.00 = モデルと実測が一致)
  boss_layer6      与 0.61  被 1.04   標本 412    ← 0.61 = 再生ぶんを取りこぼしている
  boss_layer7_p4   与 0.94  被 1.31   標本 288

1.00 から離れている敵だけがモデルの穴で、離れていなければ純関数化の動機が無い。

> **数値を動かす前に「効いているか」を数える。**

## 12. 計算量 ── 実測から逆算する（4 度目の見積もり）

**過去 3 回の誤りは全て「単位を取り違えた」ことに起因する。**
今回は実測値から出発する。

### 12-1. 実測の基礎値

`AutoRunLogs/challenge_sweep_progress.txt`（50pt・Super・ラン単位カウンタ）:

```
superWiringDecisions=121      ← 1 ラン の配線決定数
superRerollDecisions=263      ← 1 ラン のリロール決定数
superRolloutEvaluations=8712  ← 121 × 6 候補 × 12 本 = 8712 で整合
elapsedSeconds=1198.4 / 1000 ラン = 1.198 秒/ラン（50pt）
```

Super の 1 ラン あたり `ApplyTurn` 呼び出し数（概算）:

```
配線   : 121 × (列挙 ~150 + 72 ロールアウト × 平均深さ ~20) ≈ 1.9×10^5
リロール: 263 × 32 マスク × 8 標本 × TurnValue(~150) ≈ 1.0×10^7
合計 ≈ 1.0×10^7 / ラン
```

並列度 ~15 で 1.198 秒 ＝ 約 18 コア秒 → **`ApplyTurn` 1 回 ≈ 1.7 µs。**
これが以降の見積もりの単位である。

### 12-2. 構造上の修正 ── 予算の単位を仕事量そのものにする

過去 3 回の誤りはすべて「予算の単位が実際の仕事量とずれていた」ことが原因。
3 回目の誤り（「葉は単純な算術」）は**葉が再帰の入口だった**ために起きた。

> **予算は `ApplyTurn` の呼び出し回数で数える。**
> 展開した状態ノード数ではない。`ApplyTurn` は仕事の最小単位で、
> 1 回 1.7 µs と実測されているので、**予算 × 1.7 µs が時間の上界になる。**

さらに **予算は上位候補ごとに等分する**（リロールの部分集合ごとにリセットするのと同じ理由）。
共有すると先に列挙された候補だけが深く読まれ、**列挙順が答えを決めてしまう。**

### 12-3. 見積もり

| 項目 | 値 |
|---|---|
| 配線決定の予算 | 100,000 `ApplyTurn` / 決定 |
| リロールの予算 | 2,000 `ApplyTurn` / 部分集合 |
| 1 ラン の仕事量 | 121×10^5 + 263×32×2000 ≈ **2.9×10^7** |
| 単コア時間 | 2.9×10^7 × 1.7 µs ≈ 49 秒/ラン |
| 並列 ~15（Super と同じ機構） | **3〜8 秒/ラン** |
| Super 比 | 3〜7 倍 |
| 1000 ラン | **1〜2 時間** |

R6（GPU）への答え: **GPU は使わない。**§5-3 のとおり expectimax は GPU に最悪で、
`Dispatch`→`GetData` の同期が 1 決定ごとに入る形は成立しない。
代わりに Super が既に持つ `Parallel.For` + `CopySnapshotTo` のワーカー機構を流用する。
Exact は乱数を使わないので、**並列でも逐次と 1 ビット違わない**（Super より保証が強い）。

**この見積もりは 4 度目なので信用しない。** §13 の Gate 1 で 3 ラン 実測してから
予算を決める。予算が `ApplyTurn` 回数なので、**外しても時間が線形にしかずれない**
── これが 3 回のフリーズとの構造的な違い。

## 14. 実コードの読み直しで見つけたバグ（§7 に追加）

### 14-1. `ExactCombatAI._escProfile` に敵 id を入れている

```csharp
_escProfile = enemy.id;                        // ExactCombatAI（誤）
_escProfile = enemy.EffectiveEscalationProfile; // SuperCombatAI（正）
```

`Escalation.GetMultiplier(profile, turn)` は `"std"` / `"rush"` / `"gentle"` / `"spike"` で
分岐する。敵 id を渡すと**必ず `default:` に落ちて `CurveStd` になる**ので、
rush / gentle / spike の敵のエスカレーションが全部標準曲線として読まれていた。
→ Phase 2 でモデルごと移譲するので**自動的に消える**。

### 14-2. `Escalation` の 2 要素をモデルが落としている（Super も同じ）

`Escalation.EnemyAttackValue` は `倍率 × (基礎 + ダイス) × ボス倍率` だが、
Super / Exact の先読みは `倍率 × (基礎 + ダイス)` のみ。
**挑戦デバフ〈天変地異〉のボス攻撃 ×1.50 が先読みに入っていない。**
`GetBossAttackMultiplier(turn)` はターン依存なので、
高挑戦ptのボス戦で被弾を系統的に過小評価する。Phase 4 で共有モデルへ足す。

### 14-3. Super のリロールが T1〈振り直せない〉を無視している

`CombatManager.RerollPhase` は `IsLockedDie` で最終的に弾くが、コストは
`pick.Length × attempt` で**弾かれたダイスのぶんも徴収される**。
Super の `ChooseReroll` はロックを見ないので、
「振り直せないダイスに充電を払う」判断をしうる。Exact は既に除外している。
→ **モデル共有後も方策側の差として残る**（Exact が正しい）。差の解釈時に留意する。

## 15. 記録：測定で判明した関連事実

- **出目パーツは 7層クリア率をほぼ倍にする**（Optimal 18.2% → 34.7%、同一シード）。

  「ロールアウトが面添字を持たないためパーツが Super の優位を削っている」という仮説は**棄却**
- 1層ボスと 7層p1 は 5 回の測定すべてで**敗北ゼロ**。HP・挑戦pt・技量帯のいずれにも反応しない
